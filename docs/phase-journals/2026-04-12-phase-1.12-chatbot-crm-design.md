## Why this phase exists

Recall the vision from the original `agile-booping-acorn.md` plan, as captured during the EspoCRM → Twenty decision:

> **"The CRM is NOT a sales-team tool and NOT a Donny-visibility dashboard. Its real purpose is to be the data backbone for the AI chatbot as the primary customer communication channel."**
>
> "The CRM sits between the product runtime DBs and the AI chatbot. When a user asks the chatbot something, the chatbot can read their stockClient record (plan, risk profile, preferred markets, devices, watchlist) to personalize the response. Write-back enables support touchpoints + future human-in-the-loop handoff."

Twenty was specifically chosen over EspoCRM because:
1. **Native GraphQL schema introspection** → easier to build LLM tool-calls against
2. **First-class `POST /mcp` endpoint** (Model Context Protocol) → future MCP integration path
3. **Clean entity naming** (no "C" prefix) → cleaner prompt injection
4. **TypeScript ecosystem** → if we ever build a chatbot frontend in TS, direct types available

Phase 1.4-1.9 built the CRM. Phase 1.10 wired dual-write so new users have complete CRM profiles. Phase 4 wired push notifications. **This phase (1.12) is where the CRM starts paying off** by becoming a context source for the chatbot.

### What the chatbot already does for personalization

- **`sys_user_context` table** — accumulates facts about each user across chat turns. Keys like `pref/risk_tolerance`, `behavior/frequent_sectors`, `goal/timeline`. LLM-extracted, confidence-scored.
- **`build_user_context_block(user_id, limit=15)`** — turns the top-N rows into a system prompt block grouped by type.
- **`investor_profile` table** — separate structured profile (filled via onboarding flow or profile page).
- **Chat history retrieval** — last N messages injected for continuity.
- **TinyFish scan context** — retrieves relevant scan events for the current ticker.

The existing system prompt (from `context_builder.py::_ROLE`) already references:
- `[User Profile]` — risk tolerance, investment horizon, trading style, preferred language
- `[User Watchlist]` — stocks the user is tracking
- `[TinyFish Website Intelligence]` — proprietary change detection
- `[Page Context]` — what the user is viewing
- `[User Preferences]` — learned from previous conversations

### What's missing (the gap this phase fills)

1. **No Twenty CRM integration at all.** Chatbot has zero knowledge of:
   - Subscription plan (`WATCH` / `INDIVIDUAL` / `PROFESSIONAL` / `BUSINESS`) — critical for tailoring tone (free user vs paying) and feature gating
   - Device count (how many mobile devices they have registered)
   - Preferred markets (synced from watchlist via Phase 1.9')
   - Signup source (web vs mobile_ios vs mobile_android) — useful for formatting cues
   - Last login timestamp — useful for "welcome back" tone
2. **No audit trail in the CRM.** Chat conversations vanish into `sys_user_context` facts but the raw exchanges are not visible to any human (or future AI) reviewing the customer's history in Twenty.
3. **No tool calls yet.** Chatbot can't take customer-service actions (disable a notification channel, list devices, query alert history).

## Architecture options considered

### Option A — Twenty as a new READ source, sys_user_context stays independent
- Chatbot reads BOTH tables and merges into the prompt
- Pro: minimal disruption, additive, both data sources keep their strengths
- Con: two queries per chat turn

### Option B — Twenty as canonical, sync FROM sys_user_context into Twenty
- Every `sys_user_context` write also updates a field on the Twenty `stockClient` record
- Chatbot reads from Twenty only
- Pro: single source of truth
- Con: Twenty's `stockClient` doesn't have fields for fine-grained LLM-learned facts (risk_tolerance is there but investment_horizon / goal_timeline / communication_style are not). Would need schema expansion.

### Option C — sys_user_context as canonical, Twenty as mirror
- This is what the daily sync DAG already does (partial — for plan, markets, devices)
- Chatbot ignores Twenty, reads sys_user_context only
- Pro: zero chatbot code change
- Con: defeats the whole point — CRM is just a dashboard, not a chatbot backbone

### Option D — Hybrid: Twenty for structured, sys_user_context for LLM-learned (**recommended**)
- `sys_user_context` keeps its job — fine-grained LLM-learned preferences
- Twenty becomes a NEW source for **structured identity + business data**:
  - Subscription plan
  - Preferred markets (from watchlist sync)
  - Signup source
  - Device count
  - Last login
- **Chatbot reads from both**, injects both blocks into the system prompt
- They complement each other — no overlap, no drift
- **Write-back**: chatbot ALSO writes chat audit trail to Twenty as notes on the stockClient
- This is the option I'm proposing

### Option E — MCP server integration
- Twenty v1.21 exposes `POST /mcp` (Model Context Protocol)
- A Claude Desktop or MCP-compatible client could connect directly to Twenty
- Not applicable to the stock-be chatbot (which uses Gemini, not Claude) — Gemini doesn't speak MCP
- **Park for admin tooling use** (e.g. Donny browsing customer records via Claude Desktop)

## Proposed sub-phases

### 1.12.1 — Twenty READ integration (this phase, fast path)

**Goal**: chatbot system prompt gains a `[Customer Profile — from CRM]` block with Twenty stockClient data.

**New file**: `datapai-stock-be/agents/stock_chat/twenty_context.py` (~120 LOC estimated)

**Public API**:
```python
def build_twenty_context_block(email: str) -> str:
    """
    Query Twenty for the user's stockClient record by email and return a
    formatted system prompt block. Returns empty string if:
      - Twenty is unreachable (graceful degradation)
      - User has no stockClient record (legacy user pre-dual-write, or error)
      - email is None / anonymous user

    The block is short and scannable — <150 tokens — and complements the
    existing build_user_context_block() output in the assembled prompt.
    """
```

**System prompt block format** (exact output):
```
[Customer Profile — from CRM]
- Plan: INDIVIDUAL (paying user, $49 AUD/mo — use premium tone)
- Risk Profile: AGGRESSIVE
- Preferred Markets: ASX, HKEX, US
- Signup: MOBILE_IOS (mobile user — prefer short bullets, avoid tables)
- Active Devices: 2
- Last Login: 5 days ago
- Queries This Month: 10
```

Tone hints (the bracketed clarifications like "paying user, use premium tone") are built into the formatter so the LLM has explicit direction, not just raw data.

**Plan → tone mapping** (stored in the formatter for now; could be promoted to `sys_common_config` later):
- `WATCH`: `free tier — be helpful but gently mention upgrades where they unlock value`
- `INDIVIDUAL`: `paying user, $49 AUD/mo — use premium tone, no upgrade nags`
- `PROFESSIONAL`: `paying user, $299 AUD/mo — active trader, expect deeper analysis`
- `BUSINESS`: `paying user, $999 AUD/mo — team account, expect professional tone`

**Platform hints**:
- `MOBILE_IOS` / `MOBILE_ANDROID` → "mobile user — prefer short bullets, avoid tables"
- `WEB` → "web user — tables and longer content OK"
- `UNKNOWN` / `GOOGLE_OAUTH` → no hint

**Integration point**: `context_builder.py::build_full_context()` (or equivalent) already calls `build_user_context_block`. I'll add a parallel call to `build_twenty_context_block` right alongside it.

**Caching strategy** (for MVP): no caching. One Twenty GraphQL query per chat request (~20-50ms on local network). If this becomes a hot path, add a per-request in-memory cache keyed by email. Future: Redis-backed cache with 5-min TTL.

**Failure modes**:
- Twenty unreachable → log warning, return empty string, chatbot continues without the block
- Record not found → log info (normal for anonymous users or pre-dual-write legacy users whose email doesn't match an auth.users row), return empty string
- Network timeout → same as unreachable (3-second timeout, then fall back)

**No schema changes. No new DB tables. No config rows.**

### 1.12.2 — Twenty WRITE integration (chat audit trail as Notes)

**Goal**: every chatbot conversation leaves a visible note on the user's stockClient record in Twenty, so any human (or future chatbot reading its own history) can review the conversation later.

**New function**: `agents/stock_chat/twenty_context.py::log_chat_to_twenty(...)` (~80 LOC)

```python
def log_chat_to_twenty(
    *,
    email: str,
    user_message: str,
    assistant_reply: str,
    ticker: Optional[str] = None,
    exchange: Optional[str] = None,
    model: Optional[str] = None,
    tokens_used: Optional[int] = None,
    latency_ms: Optional[int] = None,
) -> bool:
    """
    Create a Note record in Twenty linked to the user's stockClient via
    noteTargets. Fire-and-forget — called AFTER the streaming response
    completes so it never blocks the user's chat.

    Returns True on success, False on any failure.
    """
```

**Twenty GraphQL — questions to resolve before coding**:

Twenty has built-in `note` and `noteTarget` objects (I saw `noteTargets: RELATION` on every custom object during Phase 1.4.7). The create flow is typically:
1. `createNote(data: { title, bodyV2: { blocknote, markdown } })` → returns `note.id`
2. `createNoteTarget(data: { noteId, stockClientId })` → links the note to the customer

I'll verify this shape with a metadata query before committing to it. If Twenty's note structure is different in v1.21.0 than what I'm assuming, this phase documents the actual API I find.

**Note format**:
- **Title**: `Chat: <first 60 chars of user's message>`
- **Body** (markdown):
  ```markdown
  **User** (2026-04-12 09:15 AEST, ticker: AAPL):
  > <full user message>

  **Assistant** (gemini-2.5-flash-lite, 850 tokens, 1.2s):
  <full assistant reply>
  ```

**Rate limiting**: no explicit limit in this phase — the existing chat budget (`chat_limits.individual_daily_limit = 500`) already caps the write volume per user per day.

**Failure mode**: if the write fails, log an error + continue. The user already got their response. The note just didn't land. A future reconciliation job could retry from `notification_log` or similar.

**Deferred**: we are NOT creating a separate `stockChatMessage` custom object. The built-in `note` is sufficient and keeps the Twenty schema clean.

## Open questions (need resolution before implementation)

1. **Twenty Note schema** — need to verify the exact GraphQL mutation shape for `createNote` + `createNoteTarget` in v1.21.0. Related: is there a single `createOneNote(input)` that accepts `noteTargets` inline? Will query the metadata API before writing code.

2. **Email lookup** — the chatbot has `user_id` (int or stock.users.id text UUID), NOT necessarily `email`. Need to resolve email from user_id at chat request time. For legacy users it's `SELECT email FROM datapai.users WHERE id = %s`. For new users (post-Phase-1.10) the same query works. Should be a single cheap read.

3. **Anonymous / unauthenticated users** — the current chatbot allows `user_id=0` (anonymous). For those, we skip both the READ and WRITE paths entirely (no email, no stockClient, no note). Needs a clear branch in context_builder.

4. **Token budget cost** — injecting the Twenty block adds ~100 tokens per chat turn. At 500 messages/month for an individual user that's 50k tokens/month extra, negligible on Gemini Flash Lite pricing. Not a concern.

5. **Privacy** — chat messages go to Twenty as notes. Any user who can access Twenty (currently just Donny as workspace admin) can read them. Fine for the current 7-user stage. Later, when a support team is added, notes become visible to more humans. This is a FUTURE privacy consideration, not a blocker for Phase 1.12.

## What's explicitly NOT in this phase

- **Tool calls** (Phase 1.12.3 future)
- **MCP server integration** (Phase 1.12.4, parked)
- **A separate `stockChatMessage` Twenty custom object** — using built-in Note instead
- **Two-way sync** (Twenty → chatbot awareness of human-authored notes) — not useful until there's a support team
- **Prompt injection protection** on the note body — we don't render note bodies back into the LLM context, so no amplification risk
- **Deep links from Twenty note UI back to the mobile app** — no mobile deep link scheme for chat messages yet
- **Chat history recall from Twenty** — we'd read chat history from the local Postgres (as the existing code does) not from Twenty notes. Twenty notes are write-only for this phase.
