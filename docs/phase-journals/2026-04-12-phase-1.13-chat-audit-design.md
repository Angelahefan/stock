## Why this phase exists

Three problems, one fix:

1. **Chat history has been silently broken since ~2026-04-02** (last successful chat_messages row). Every authenticated chat since then has been getting ephemeral session_id=null + "Message persist failed (non-fatal)" warnings. Root cause: `datapai.chat_sessions` + `datapai.chat_messages` are `postgres_fdw` foreign-table aliases on `stock_db` pointing to real tables on `framework_db`. INSERTs via the FDW send the full column list with NULL for unspecified columns, bypassing remote `DEFAULT gen_random_uuid()` / `nextval()` / `NOW()` clauses.

2. **AI governance requirement (NEW standing rule)**: every AI conversation must be persisted and auditable. No black-box AI at DATAP.AI. Applies to stock AND healthcare AND any future vertical.

3. **Cold data archival**: the `chat_messages` table will grow unbounded if we just fix the write path. Need a hot (90-day Postgres) / cold (forever S3 Parquet) boundary enforced by a weekly DAG.

## Concrete decisions (autonomous)

### Hot retention window: 90 days

Stored in `sys_common_config` under a new config_type:

```sql
INSERT INTO datapai.sys_common_config (config_type, config_key, config_value, description, created_by)
VALUES
  ('chat_archive', 'hot_retention_days', '90',
   'Number of days chat messages stay in Postgres before archival to S3',
   'phase_1_13_2026-04-12'),
  ('chat_archive', 'archive_bucket', 'codepais3',
   'S3 bucket name for chat history cold storage',
   'phase_1_13_2026-04-12'),
  ('chat_archive', 'archive_prefix', 'datapai-archive/stock/chat_history',
   'S3 key prefix under the bucket (the vertical domain goes here — stock/health/etc)',
   'phase_1_13_2026-04-12'),
  ('chat_archive', 'archive_enabled', 'true',
   'Master kill-switch for the archival DAG. Set false to pause archival without disabling the DAG.',
   'phase_1_13_2026-04-12');
```

All 4 values are loaded at DAG runtime — no hardcoding. Changing retention to 180 days is a single SQL UPDATE.

### S3 layout

- **Bucket**: `codepais3` (existing, ap-southeast-2, IAM role already has access)
- **Prefix**: `datapai-archive/stock/chat_history/`
- **Partitioning**: Hive-style `year=YYYY/month=MM/day=DD/` based on `chat_messages.created_at`
- **File naming**: `part-00000.parquet` (single file per partition for now; can shard later if daily volume grows)
- **Compression**: snappy (default for pyarrow, good balance of size + read speed)
- **Schema** (one row per chat_message, with session context denormalized for audit queryability):

```
message_id         int64
session_id         string (UUID)
user_id            int32
session_user_id    int32    (same as user_id but kept for JOIN-free queries)
ticker             string
exchange           string
session_title      string
session_created_at timestamp[us, UTC]
role               string  (user | assistant)
content            string  (full, untruncated)
model_used         string
tokens_used        int32
context_sources    string  (JSON-as-string)
created_at         timestamp[us, UTC]
archived_at        timestamp[us, UTC]
archive_run_id     string  (for traceability to the DAG run)
```

### Why fix history.py, not patch the FDW alias

I considered three fixes:

| Option | Pro | Con |
|---|---|---|
| **(A) Route writes through direct framework_db conn** ✅ chosen | Clean, reuses the `_get_framework_conn` pattern from `send_alerts.py`. Works for any FDW table. | history.py needs a slight refactor — but it's already small. |
| (B) `ALTER FOREIGN TABLE` to drop id/created_at columns so postgres_fdw doesn't send them | Minimal code change | Breaks SELECT queries that filter on `created_at`. Non-starter. |
| (C) Include explicit `nextval()` + `NOW()` in the INSERT literal | Works without code refactor | Brittle — couples to sequence names, fails if schema changes, every future table needs the same treatment |

**Option A wins.** It establishes the write-path rule for ALL future framework_db tables and avoids the same bug recurring.

### Backfill of the lost ~10 days

The gap is April 2 → April 12. During this window:
- User messages were sent to the LLM and replies were returned
- The persist attempt failed silently ("non-fatal" log)
- The raw data is gone — not in any local file, not in any in-process buffer

**I cannot recover this data.** The AI governance rule says "never swallow errors" and this is exactly why. I'll note the gap in the audit log as a known blackout period, fix the root cause so it never happens again, and add a startup check that fails loudly if persist is broken.

The 90-day window therefore has a gap from April 2 → April 12. After the fix ships, every new message from April 12 onwards will be captured.

### AI governance write-path test (mandatory post-fix)

Before declaring Phase 1.13 done, I must prove that:
1. A chat message from donny persists to `chat_messages` (hot tier)
2. If `framework_db` is momentarily unreachable, the error is LOUD (metric + audit log), not silent

### Schema changes to `chat_sessions` and `chat_messages`

**None.** The existing columns are sufficient. The only new table is `sys_archive_log` (for DAG run auditability):

```sql
CREATE TABLE IF NOT EXISTS datapai.sys_archive_log (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    run_id          TEXT NOT NULL,
    domain          TEXT NOT NULL,  -- 'stock' | 'health' | ...
    source_table    TEXT NOT NULL,  -- 'chat_messages'
    s3_bucket       TEXT NOT NULL,
    s3_key_prefix   TEXT NOT NULL,  -- datapai-archive/stock/chat_history/year=YYYY/month=MM/day=DD/
    rows_exported   INT  NOT NULL,
    rows_deleted    INT  NOT NULL,
    bytes_uploaded  BIGINT,
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at     TIMESTAMPTZ,
    status          TEXT NOT NULL DEFAULT 'running',  -- running | success | failed
    error_detail    TEXT
);
CREATE INDEX IF NOT EXISTS idx_sys_archive_log_domain_table_started
  ON datapai.sys_archive_log(domain, source_table, started_at DESC);
```

This gives ops a clean audit trail: "when did we last archive chat history? how many rows? any failures?"

### Phase 1.14 (#4) scope — frontend user_id fix

Not strictly part of the audit fix, but directly related. The current `parseInt(UUID, 10)` collapses e.g. `9974f810-...` → `9974` which:
1. Makes `_get_user_plan()` fail (can't match 4 digits against a full UUID → every user treated as `watch`)
2. Risks collisions once we have >~100 users
3. Makes audit queries harder (can't JOIN chat rows to auth.users by id reliably)

**Fix**: change the Next.js chat routes to send `user_id: user.userId` (the full UUID string) as a new field alongside the legacy `user_id: int`. Python endpoint accepts both — prefers UUID if present, falls back to legacy int for backward compat. `twenty_context.py::_get_email_from_user_id` already handles both shapes (from Phase 1.12).

**3 files to change**: `app/api/ticker/[symbol]/chat/route.ts`, `app/api/ticker/[symbol]/chat/stream/route.ts`, `app/api/copilot/stream/route.ts` + the `ChatRequest` Pydantic model.

## Verification plan

### Unit-level (Python shell)

1. `save_message("<fake-uuid>", "user", "test", ...)` → no exception, row visible in `chat_messages` via Postgres query
2. `create_new_session(9974, "AAPL", "US")` → returns a UUID, row visible in `chat_sessions`
3. `get_or_create_session(9974, "AAPL", "US")` called twice → returns the same id on the second call (idempotent)

### End-to-end (HTTP chat request)

1. Restart `datapai-agent.service`
2. `curl POST /agent/stock-chat` with donny
3. Check response contains a real `session_id` (not null!)
4. Query `chat_sessions` — new row with donny's user_id + ticker
5. Query `chat_messages` — two new rows (user + assistant) with real `id` values
6. Check `auth.audit_log` for a `chat_persist_success` event or equivalent
7. Query Twenty for the new Note (should still work — Phase 1.12.2 path unaffected)

### Archival DAG dry-run

1. Seed a few old rows in `chat_messages` with `created_at = now() - interval '100 days'`
2. Run `scripts/archive_chat_history_to_s3.py --dry-run`
3. Verify:
   - S3 Parquet file created under `datapai-archive/stock/chat_history/year=2026/month=01/day=02/` (or similar)
   - Row count matches
   - Parquet is readable via `pd.read_parquet()`
   - Postgres rows are NOT yet deleted (dry-run)
4. Re-run without `--dry-run`
5. Verify Postgres rows are deleted
6. `sys_archive_log` has a `status='success'` row

### #4 frontend test

1. Log in as donny in the mobile app or web
2. Send a chat request
3. Verify `chat_sessions.user_id` is the legacy int (unchanged) AND a new column or extension captures the UUID correctly
4. `twenty_context._get_email_from_user_id` resolves correctly via direct UUID match (not LIKE prefix)

## What's NOT in this phase

- **GDPR right-to-erasure path** — design only, implement when legally required
- **Athena query layer** — just Pandas-on-demand reads for now; Athena can be added when an audit needs SQL-over-Parquet at scale
- **Healthcare chat** — parallel implementation when the healthcare copilot ships. The rule applies; the code is per-domain
- **Chat `content` encryption at rest** — KMS encryption is enabled by default on most S3 buckets; confirmed and documented, not changed here
- **Backfill of the April 2 → April 12 gap** — raw data is lost, no possible recovery
