## What shipped (30-second summary)

Every AI chat interaction at DATAP.AI now has a two-tier audit trail:
- **Hot tier (90 days):** `datapai.chat_sessions` + `datapai.chat_messages` on `framework_db`, written via **direct psycopg2 connection** (not the stock_db FDW alias — that's the bug this phase fixes).
- **Cold tier (forever):** Weekly Airflow DAG exports everything older than 90 days to `s3://codepais3/stock/raw/chat_history/year=YYYY/month=MM/day=DD/*.parquet` (Hive-partitioned), verifies readability, then deletes from Postgres.

**Two bugs fixed:**
1. **FDW DEFAULT-bypass bug** (pre-existing, silently dropping chat history since ~2026-04-02). `datapai.chat_sessions` + `chat_messages` + `user_preferences` + `sys_user_context` are **foreign-table aliases** on `stock_db` pointing at real tables in `framework_db`. postgres_fdw sends the full column list with NULLs for fields not in VALUES, bypassing the remote-side `DEFAULT gen_random_uuid()` / `NOW()` clauses. Result: INSERTs failed with "null value in column id violates not-null constraint" and were swallowed by `logger.warning("...non-fatal...")` in the endpoint. No chat had been persisted for 10 days.
2. **Silent failure pattern.** Any exception during chat persistence was caught and logged at WARNING. That's a governance violation — a failed audit record is NOT non-fatal. Upgraded to ERROR with a `GOVERNANCE:` prefix so it shows up in monitoring / journalctl.

Plus Phase 1.14 (`#4`): Next.js `parseInt("9974f810-...")` truncates UUIDs to 4-digit prefixes before sending to the backend. The 3 chat routes now send the full `user_uuid` alongside the legacy `user_id` int, and the backend prefers the uuid when available.

## Architecture

### Hot path — writing a chat message

```
  Next.js chat route
    POST /api/ticker/AAPL/chat
    { user_id: 9974, user_uuid: "9974f810-...", ticker, exchange, message, ... }
       │
       ▼
  datapai-stock-be /agent/stock-chat (endpoint.py)
       │
       │ user_id_for_context = user_uuid ?? str(user_id)
       │
       ├──▶ get_or_create_session()           ┐
       │    save_message(user, role=user)    │  via stock_chat/fw_db.py
       │    save_message(ai,   role=assist)  │  direct psycopg2 to framework_db
       │    extract_user_context_fast()      │  port 5433, auth_service user
       │    extract_and_save_preferences()   ┘
       │
       └──▶ log_chat_to_twenty() (Phase 1.12, secondary audit — non-fatal)
```

**Key change:** all writes route through `agents/stock_chat/fw_db.py` — a new shared module that holds a direct psycopg2 connection to `framework_db` (port 5433, `auth_service` user). Reads continue to use `.db` (stock_db FDW pool) because reads through the FDW are transparent and fast — it's only writes that are broken.

### Cold path — weekly archival to S3

```
  Airflow DAG: chat_history_archival  (every Sun 02:00 UTC)
       │
       ▼
  run_archive_chat_history_to_s3.sh
       │
       ▼
  scripts/archive_chat_history_to_s3.py
    1. Load config from sys_common_config (DB-driven, no hardcoding)
       hot_retention_days=90, archive_bucket=codepais3, archive_enabled=true, ...
    2. INSERT sys_archive_log (status='running')
    3. SELECT * FROM chat_messages LEFT JOIN chat_sessions
         WHERE m.created_at < NOW() - INTERVAL '90 days'
       → 15 enriched columns (message + session metadata)
    4. Group by DATE(created_at AT TIME ZONE 'UTC')
    5. For each day:
         a. Serialize to Parquet (pyarrow + snappy)
         b. S3 put_object → year=YYYY/month=MM/day=DD/part-00000-<run_id>.parquet
         c. Download + re-read → row count must match
         d. DELETE FROM chat_messages WHERE id IN (...)
    6. Clean up orphaned sessions (no remaining messages)
    7. UPDATE sys_archive_log (status='success' or 'failed' or 'partial')
```

**Rollback semantic:** the Parquet files are canonical. If a human ever wants to restore, the S3 files are the source of truth — not the Postgres copy (which is just the hot cache).

## Configuration (DB-driven, no hardcoded values)

| config_key | Default | What it does |
|---|---|---|
| `hot_retention_days` | `90` | Postgres retention. Rows older than this get archived + deleted. |
| `archive_bucket` | `codepais3` | S3 bucket. Already exists in ap-southeast-2, shared with other archive loads. |

## Gotchas discovered (captured so we don't trip again)

### 1. postgres_fdw always sends full column list with NULLs

**Symptom:** "null value in column id violates not-null constraint, CONTEXT: remote SQL command UPDATE..."
**Why:** postgres_fdw builds a cross-node INSERT that lists every column, filling unspecified ones with NULL. The remote's `DEFAULT gen_random_uuid()` never runs because the column has an explicit value (NULL).
**Fix:** route writes through a direct psycopg2 connection that targets the remote database directly. Do NOT go through the FDW alias.
**Pattern:** `agents/stock_chat/fw_db.py` (same pattern as `scripts/send_alerts.py::_get_framework_conn` from Phase 4A).
**Rule:** for any table on `framework_db` with DEFAULT clauses on id/created_at/etc., the write path MUST use `fw_db`, not `.db`. Reads through `.db` (FDW) stay fast + transparent.

### 2. Silent audit failures are a governance violation

Old pattern (everywhere in stock_chat):
```python
try:
    save_message(...)
except Exception as e:
    logger.warning("persist failed (non-fatal): %s", e)
```
This swallowed the FDW bug for 10 days. The user who flagged the standing rule put it bluntly: *"we can't leave black box for AI."*

New pattern:
```python
try:
    save_message(...)
except Exception as e:
    logger.error(
        "GOVERNANCE: chat persist FAILED for session=%s user_id=%s ticker=%s: %s",
        session_id, user_id_str, ticker, e,
    )
```
Still graceful (the user gets their chat response), but loud enough that monitoring / journalctl will surface it within the next alert window.

### 3. The Next.js `parseInt(UUID)` quirk

The frontend's `getAuthUser().userId` returns a TEXT UUID like `"9974f810-e93d-4a78-b3bd-02a08a2f6de4"`. The chat routes did:
```ts
const userId = parseInt(user.userId, 10) || 0;
// → 9974 (parseInt stops at the first non-digit)
```
Then shipped `user_id: 9974` to the backend. This was fine for rows like `sys_user_context` that use prefix LIKE matching (Phase 1.12 workaround), but wrong in principle — the backend couldn't reliably resolve the full user identity.

**Fix (Phase 1.14):** every chat route now also captures `userUuid = user.userId` (the full string) and sends it as a new `user_uuid` field alongside the legacy int. Backend prefers `user_uuid` when non-empty, falls back to `str(user_id)` otherwise.

### 4. psycopg2 autocommit + broken connection recovery

The `fw_db._fw_cursor()` context manager catches `OperationalError` / `InterfaceError`, drops the cached connection so the next call reopens it. Autocommit mode means each `cur.execute()` is independent — no half-written transactions to worry about, at the cost of losing explicit multi-write atomicity (save_message + touch session updated_at are NOT atomic, which is fine for an audit trail that tolerates last-write-wins on the updated_at column).

## Rollback plan

Every change is independently revertible:

1. **If the write-path fix misbehaves**: `git revert <commit>` on stock-be brings back the old FDW-alias writes. They'll fail with the same NULL-constraint error they had before, but the error-swallowing safety net is still in place so the live site keeps serving chat responses (just without persistence).
2. **If archival script misbehaves**: the DAG is `is_paused_upon_creation=True`. It won't run automatically. Drop the DAG file and `airflow dags delete chat_history_archival` if needed.
3. **If Postgres fills up** before archival runs: manually run the script with `--dry-run` first, then without, to catch up. It's safe to run ad-hoc.
4. **If S3 archival is accidentally destructive**: sys_archive_log has a row for every run with start/end timestamps and row counts. Cross-reference against S3 object listings.
5. **Frontend user_uuid rollback**: revert the 3 route files; backend is backward-compatible (still handles missing `user_uuid` by falling back to legacy int).

## One-paragraph summary for the investor deck slide

> DATAP.AI's AI chatbot (primary customer communication channel across stock and health verticals) now has an end-to-end audit trail that satisfies AI governance requirements for regulated industries. Every conversation — user message, AI response, model, token count, context sources — is persisted to Postgres (hot tier, 90-day retention) and archived weekly to S3 as Parquet (cold tier, forever). The write path bypasses a known postgres_fdw bug via a dedicated direct-connection writer module. Archival runs on Airflow with full run-audit logging (start time, row count, Parquet verification, dry-run support). Configuration is database-driven — retention, bucket, prefix, and kill switch all change via SQL with zero code. No black box.
