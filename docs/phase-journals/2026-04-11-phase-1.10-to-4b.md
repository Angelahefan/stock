**Key points that tripped us up and are now captured**:
- `datapai.users` lives in `framework_db`, not `stock_db`. The stock DB sees it via a postgres_fdw foreign-table alias.
- `auth.users` and `datapai.users` live in the same physical database (`datapai_auth_db`), just different schemas. So "dual-write" is a same-connection 2-row INSERT, not a cross-container operation.
- 28 tables on stock_db are FDW aliases pointing at framework_db. Only stock-market tables (prices, ohlcv, synthesis, indicators) are real on stock_db.
- `usr_notification_prefs` is the exception — it's a REAL local table on stock_db, not an FDW alias. It holds the per-user Telegram/email channel opt-ins and `telegram_chat_id`.
- FDW INSERT always sends the full column list with NULLs for columns not explicitly provided, bypassing remote-side DEFAULT clauses. This is the `_log_notification` gotcha (see "Gotchas" section).
- The current stock-be code refers to `datapai.users.id` as if it's a UUID string. For legacy users it's the old self-assigned UUID. For NEW users (post-2026-04-11), it's `auth.users.uuid` (same value in both tables). Donny's legacy id `9974f810-...` does NOT match his auth.users.uuid `af7a00e6-...` — unmigrated historical debt.

## Phase 1.10 — Dual-write + device registration

### Motivation

Before this phase: new user registers via `/api/auth/register` → row in `auth.users` only → stock app's `_get_user_plan(user_id)` query returns nothing → fallback to `'watch'` → broken experience. The 7 legacy users worked (they had both rows from a one-off migration), but no NEW user could ever get a complete stock profile without manual intervention.

### Design

1. On successful `INSERT INTO auth.users ... RETURNING id, uuid`, immediately `INSERT INTO datapai.users (id, email, password_hash, plan, plan_status, created_at, preferred_lang, signup_source) VALUES (uuid, ...)` on the same psycopg2 connection.
2. Use the **auth.users.uuid** as the `datapai.users.id`. Closes the provisioning gap and makes the JWT's `uuid` claim directly usable for stock-side lookups going forward.
3. Failure of the dual-write is logged + audited but does NOT rollback the `auth.users` insert. Auth availability must not depend on legacy-schema availability. A reconciliation DAG (future) can clean up orphans.
4. Same pattern applied to the Google OAuth register branch (`signup_source='google_oauth'`, `password_hash='oauth_only'`).

### Migration SQL

Applied via `docker exec -i datapai_framework_db psql ... <<SQL`. The DDL is persisted at `migrations/040_phase_1_10_dual_write.sql` in this repo for reproducibility in other environments.

```sql
-- On datapai_framework_db.datapai schema
ALTER TABLE datapai.users
  ADD COLUMN IF NOT EXISTS signup_source TEXT NOT NULL DEFAULT 'unknown';

ALTER TABLE datapai.users
  ADD CONSTRAINT users_signup_source_check
  CHECK (signup_source IN ('web', 'mobile_ios', 'mobile_android', 'google_oauth', 'unknown'));

CREATE TABLE IF NOT EXISTS datapai.user_devices (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         TEXT NOT NULL,
    platform        TEXT NOT NULL CHECK (platform IN ('ios', 'android', 'web')),
    expo_push_token TEXT,
    device_name     TEXT,
    device_model    TEXT,
    os_version      TEXT,
    app_version     TEXT,
    last_seen_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    disabled_at     TIMESTAMPTZ,
    UNIQUE (user_id, expo_push_token)
);

CREATE INDEX IF NOT EXISTS idx_user_devices_user
  ON datapai.user_devices(user_id) WHERE disabled_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_user_devices_push_token
  ON datapai.user_devices(expo_push_token)
  WHERE expo_push_token IS NOT NULL AND disabled_at IS NULL;

-- auth_service is the FastAPI role for auth-be
GRANT USAGE ON SCHEMA datapai TO auth_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA datapai TO auth_service;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA datapai TO auth_service;
ALTER DEFAULT PRIVILEGES IN SCHEMA datapai
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO auth_service;
```

Plus FDW alias refresh on `datapai_stock_db`:

```sql

```

## Phase 4A — `_log_notification` FDW gotcha fix (pre-existing production bug)

### The symptom

During the push smoke test, `send_alerts.py` crashed with:

```
psycopg2.errors.NotNullViolation: null value in column "id" of relation "notification_log" violates not-null constraint
DETAIL: Failing row contains (null, 9974f810-..., telegram, ATRC, US, signal_alert:SELL, sent, null, null).
CONTEXT: remote SQL command: INSERT INTO datapai.notification_log(id, user_id, channel, ticker, exchange, message_type, status, error_detail, sent_at) VALUES ($1, $2, $3, $4, $5, $6, $7, $8, $9)
```

**Critical finding**: this was NOT caused by my new push-loop code. It's the existing `_log_notification` function crashing. The original author wrote:
```python
cur.execute(
    "INSERT INTO datapai.notification_log "
    "(user_id, channel, ticker, exchange, message_type, status, error_detail) "
    "VALUES (%s, %s, %s, %s, %s, %s, %s)",
    (user_id, channel, ticker, exchange, message_type, status, error_detail),
)
```

**This SQL is correct for a normal table** — it omits `id` and `sent_at`, expecting the remote-side `DEFAULT nextval(...)` and `DEFAULT NOW()` to fire.

But `datapai.notification_log` on `stock_db` is an **FDW foreign-table alias** pointing to the real table on `framework_db`. `postgres_fdw` always sends the **full column list** (all 9 columns from the foreign table definition) with NULL for any column not in the local INSERT. The `DEFAULT` clauses exist on the REMOTE side, but `postgres_fdw` passes an explicit NULL, so the defaults never fire. The remote side then rejects the row because `id IS NULL` violates the `NOT NULL` constraint.

### Why it was dormant

`send_alerts.py` has been in production for weeks, writing to `notification_log`... but it **has never actually fired a signal change with a matching eligible user** until today. The Telegram loop only writes when:
1. A signal change is detected (uncommon — most EOD runs find zero changes)
2. AND an eligible user exists (`usr_notification_prefs.channel='telegram' AND enabled=TRUE AND telegram_chat_id IS NOT NULL AND alert_signal=TRUE`)
3. AND the user's watchlist includes the changed ticker
4. AND the daily budget isn't exhausted

Until today, condition (2) had zero rows — nobody had linked Telegram. My Phase 4A work linked donny, and the very next smoke test (which fabricated condition 1 via a synthetic signal change) crashed on condition 4→5. This had been a timebomb waiting for the first real signal change after the first user linked a channel.

### The fix

Route `_log_notification` through a direct framework_db connection instead of the stock_db FDW. The real table honors its own DEFAULT clauses. Same treatment for `_disable_invalid_push_token` (same FDW-goes-through-user_devices issue).

```python
_framework_conn = None

def _get_framework_conn():
    global _framework_conn
    if _framework_conn is None or _framework_conn.closed:
        _framework_conn = psycopg2.connect(
            host=os.getenv("AUTH_DB_HOST", "localhost"),
            port=int(os.getenv("AUTH_DB_PORT", "5433")),
            dbname=os.getenv("AUTH_DB_NAME", "datapai_auth_db"),
            user=os.getenv("AUTH_DB_USER", "auth_service"),
            password=os.getenv("AUTH_DB_PASSWORD", ""),
        )
        _framework_conn.autocommit = True
    return _framework_conn


def _log_notification(conn, user_id, channel, ticker, exchange, message_type, status, error_detail=None):
    # `conn` kept for backward compatibility with call sites but unused — we
    # now use a direct framework_db connection to bypass the FDW default-value gotcha.
    fw = _get_framework_conn()
    with fw.cursor() as cur:
        cur.execute(
            "INSERT INTO datapai.notification_log "
            "(user_id, channel, ticker, exchange, message_type, status, error_detail) "
            "VALUES (%s, %s, %s, %s, %s, %s, %s)",
            (user_id, channel, ticker, exchange, message_type, status, error_detail),
        )
```

Alternatives considered and rejected:
- **Use `DEFAULT` keyword explicitly in the INSERT** — `postgres_fdw` parameterizes everything; `DEFAULT` becomes `$1 = null` in the remote. Doesn't work.
- **Recreate the foreign table without `id` and `sent_at` columns** — breaks SELECT queries that filter on `sent_at >= CURRENT_DATE`.
- **BEFORE INSERT trigger on the foreign table** — postgres_fdw doesn't support triggers on foreign tables for this purpose.
- **Query `nextval()` client-side and pass it as a literal** — works but couples the script to the sequence name, and still has the problem for `sent_at`.

The direct-framework connection approach is the cleanest and is now captured in `docs/architecture/fdw-gotchas.md` as a reusable pattern for other scripts.

```python
def _load_push_daily_limits(conn) -> dict[str, int]:
    """
    Load plan-specific push notification daily limits from sys_common_config.
    Returns: {"watch": 5, "individual": 20, "professional": 50, "business": 100, "_default": 5}
    """
    limits: dict[str, int] = {}
    try:
        with conn.cursor() as cur:
            cur.execute("""
                SELECT config_key, config_value FROM datapai.sys_common_config
                WHERE config_type = 'push_limits'
                  AND (effective_from IS NULL OR effective_from <= CURRENT_DATE)
                  AND (effective_to   IS NULL OR effective_to   >  CURRENT_DATE)
            """)
            for key, value in cur.fetchall():
                plan_id = "_default" if key == "default_daily_limit" else key.removesuffix("_daily_limit")
                try:
                    limits[plan_id] = int(value)
                except (TypeError, ValueError):
                    logger.warning("push_limits.%s has non-int value %r, skipping", key, value)
    except Exception as e:
        logger.warning("failed to load push_limits config, using defaults: %s", e)
    if "_default" not in limits:
        limits["_default"] = 5  # safety net
    return limits
```

## Gotchas

### 1. postgres_fdw INSERT bypasses remote-side DEFAULT clauses

Captured in detail under "Phase 4A — `_log_notification` FDW gotcha fix" above.

**Rule**: any INSERT against a stock_db FDW-aliased table that relies on remote DEFAULT clauses will fail with `NOT NULL` violations. Either provide every column value explicitly, OR route the write through a direct framework_db connection (preferred, cleaner).

### 2. Twenty `objects(paging)` truncates nested `fields`

`query { objects(paging: { first: 200 }) { edges { node { fields(paging: { first: 200 }) { edges { node { ... } } } } } } }` returned only 6 of 22 fields for stockClient, selected in no apparent order. The inner `fields` pagination is NOT honored inside the outer `objects` query.

**Workaround**: query per-object using `object(id: $objectId) { fields(paging: { first: 200 }) { ... } }`. This matches how `bootstrap_twenty_objects.py` does it and returns all fields reliably.

### 3. ALTER TABLE on a FDW foreign table only changes LOCAL metadata

Running `ALTER TABLE datapai.users ADD COLUMN signup_source TEXT` on `stock_db` (where `datapai.users` is an FDW alias) adds the column to the LOCAL foreign-table definition, making `stock_db` think the remote has that column. The actual remote `framework_db.datapai.users` table is NOT modified. Any SELECT that references `signup_source` from the stock-db side will then fail with `"column does not exist, CONTEXT: remote SQL command"`.

**Rule**: ALWAYS apply schema migrations on `framework_db` FIRST (the real table), THEN refresh the FDW foreign-table alias on `stock_db` via `ALTER FOREIGN TABLE ... ADD COLUMN ...`. Never run `ALTER TABLE` on the stock-db side expecting it to propagate.

### 4. Schema-level `GRANT USAGE` must come before table-level grants

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON datapai.users TO auth_service;  -- silently useless without USAGE
```

First smoke test failed with `permission denied for schema datapai`. Need the schema-level grant first:

```sql
GRANT USAGE ON SCHEMA datapai TO auth_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA datapai TO auth_service;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA datapai TO auth_service;
ALTER DEFAULT PRIVILEGES IN SCHEMA datapai
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO auth_service;
```

The `ALTER DEFAULT PRIVILEGES` line ensures any future tables created in the schema automatically get the grants — no need to remember to re-grant for new tables.

### 5. Airflow DAG `start_date` in the future silently breaks manual triggers

If you set `start_date=datetime(tomorrow, ...)` and `airflow dags trigger <dag>`, Airflow creates a DagRun that goes to `success` state in **~8ms with ZERO task instances ever created** — no error, no log, just silent no-op. The scheduler filters out all tasks whose logical_date is before start_date, even for manual runs.

**Rule**: `start_date` should always be at least yesterday (or earlier). Diagnosed this during Phase 1.6'-1.9' initial deploy — wasted 30 min chasing it before realizing the pattern.

### 6. Airflow bind-mount inode cache staleness

`/home/ec2-user/.env.dev` is bind-mounted into the Airflow scheduler container at `/opt/datapai/.env.dev`. If the host file ever gets rewritten via `sed -i` or similar (which creates a new file with a new inode), the container keeps seeing the OLD inode until you restart the scheduler.

**Diagnose**: `stat -c "%i %s %Y" <path>` on host vs `docker exec <container> stat -c "%i %s %Y" <path>` — different inodes = broken.

**Fix**: `docker compose -f docker-compose.datapai.yml restart airflow-scheduler`.

### 7. Twenty SELECT field quirks

1. Option `id` must be a real UUID (strings like `"conservative-id"` rejected)
2. Option `value` must be `UPPER_SNAKE_CASE` (lowercase like `"watch"` rejected)
3. `defaultValue` must be a string with embedded single quotes — e.g. `"'WATCH'"`, not `"WATCH"`
4. BOOLEAN field `defaultValue` must be `"'false'"` or `"'true'"`, not raw `"false"`
5. Datetime fields want strict `YYYY-MM-DDTHH:mm:ssZ` format — no microseconds, `Z` suffix not `+00:00`. Use `dt.astimezone(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")`, NOT `.isoformat()`.

1. Adding JWT verification middleware to stock-be (similar to auth-be's pattern)
2. Extracting `uuid` from the JWT
