### User-id resolution (NEW decision not in the design doc)

**Problem**: the chat endpoint accepts `user_id: int` but donny's `datapai.users.id` is a text UUID like `9974f810-2256-4f65-82d0-6639c3fd6124`. Tracing the frontend code I found that `datapai-stock-fe/app/api/ticker/[symbol]/chat/route.ts` does:

```typescript
userId = parseInt(user.userId, 10) || 0;   // best-effort for legacy key
```

JavaScript's `parseInt` reads leading digits and stops at the first non-digit, so `parseInt("9974f810-...")` returns `9974`. The stock-be chat endpoint has been receiving this 4-digit prefix as the "user id" for months. The existing `_get_user_plan(user_id)` does `str(user_id)` and queries `WHERE id = %s` — which **never matches** the full UUID. So in production, `_get_user_plan` silently falls back to `'watch'` for every real user. The whole per-user plan check in chat has been a no-op.

**My fix in `_get_email_from_user_id`**: two-strategy lookup:
1. If `len(user_id_str) >= 32`: direct UUID match (`WHERE id = %s`)
2. Else: prefix match (`WHERE id LIKE '<user_id>%' ORDER BY created_at DESC LIMIT 1`)

Collision risk: with a 4-digit prefix against base-16 UUIDs, a collision happens roughly 1-in-10000. At the current 7 users + handful of new test registrations, zero collisions today. Worth noting for future scale — if we ever have 1000+ users, the frontend's `parseInt` approach will start causing wrong-user attribution and should be fixed at the frontend layer (pass the full UUID or email through instead of the truncated int).

I **did not fix the frontend**. Out of scope. Documented as a follow-up item.

### Client caching strategy

One `TwentyClient` instance per Python process, lazily initialized on first call, cached in a module-level `_twenty_client`. If init fails (missing API key, Twenty down at startup), we set `_twenty_client_init_failed = True` and subsequent calls return early without retrying. The user_id → email lookup is a cheap Postgres query so I don't cache it (keeps code simple).

**Why no per-request retry on init failure**: if Twenty is down when the first chat request fires, every subsequent request would waste 3+ seconds on a connection timeout. The flag lets us degrade cleanly and the chatbot keeps working. The flag is reset on process restart, which happens every few days as the service gets redeployed anyway.

### Fire-and-forget WRITE

`log_chat_to_twenty` is called synchronously from the persist block in `endpoint.py`, but:
- It's called AFTER the assistant reply has already been computed and the response is about to be returned
- Failures are wrapped in try/except at the call site AND inside the function itself
- A 2-hop write (create note → create noteTarget) takes ~200ms on localhost which is acceptable for a synchronous call

**I did NOT spawn a background task** (e.g. `asyncio.create_task` or `ThreadPoolExecutor.submit`) because:
1. The non-streaming `/agent/stock-chat` endpoint is synchronous (not async), so starting a thread is awkward
2. The streaming `/agent/stock-chat/stream` endpoint already completes the user's SSE stream BEFORE the persist block runs — so the synchronous write doesn't affect user-perceived latency
3. Adding async complexity increases the bug surface for marginal gain

If the write becomes a latency bottleneck later (e.g. Twenty gets slow), revisit with a proper async-task pattern.

### Note body truncation

Hard caps: 8000 chars for user message, 12000 chars for assistant reply. Beyond those, I append `*(truncated)*` in italics. This prevents catastrophic note bloat if a user pastes a massive wall of text. Typical chat messages are ~200-1000 chars so this rarely triggers.

### Plan-based tone hints kept inline, not DB-driven

The "INDIVIDUAL → paying user ($49 AUD/mo) — use premium tone" mapping is inline Python in `_plan_tone_hint()`. Per the standing DB-driven principle this **should** be in `sys_common_config` eventually. I didn't promote it because:
1. It's a trivial 4-entry mapping that won't evolve often
2. Changing tone hints requires LLM prompt tuning to validate — not something you want changing via SQL at 3am
3. It depends on plan identifiers that already live in Twenty and `sys_pricing_tiers` — the enum values ARE DB-driven; only the prose hints are static

Flagged as a future refinement if a non-engineer ever wants to tune chatbot tone per plan.

## Pre-existing bugs I discovered (NOT fixed — out of scope)

While testing my new code, I ran into errors in the chat service logs that are unrelated to my changes. These are pre-existing production bugs in the chat history persistence path. Same FDW class of bug as the `_log_notification` one I fixed yesterday.

### Bug 1: `chat_sessions` INSERT crashes with NOT NULL id

From the service logs:
```
Session setup failed (using ephemeral): null value in column "id" of relation "chat_sessions" violates not-null constraint
DETAIL:  Failing row contains (null, 9974, AAPL, US, AAPL AI Analysis Chat, null, null).
CONTEXT:  remote SQL command: INSERT INTO datapai.chat_sessions(id, user_id, ticker, exchange, title, created_at, updated_at) VALUES ($1, $2, $3, $4, $5, $6, $7) RETURNING id
```

Root cause: `datapai.chat_sessions` on stock_db is an FDW foreign-table alias pointing to the real table on framework_db. The INSERT via `postgres_fdw` sends the full column list with `NULL` for `id`, bypassing the remote-side `DEFAULT gen_random_uuid()` clause. This is **the same exact bug class** as yesterday's `_log_notification` fix.

### Bug 2: `chat_messages` INSERT same issue

```
Message persist failed (non-fatal): null value in column "id" of relation "chat_messages" violates not-null constraint
DETAIL:  Failing row contains (null, 6cca9ecd-bf47-4384-8aa9-511db38e61aa, user, Phase 1.12 test — ..., null, null, [], null).
CONTEXT:  remote SQL command: INSERT INTO datapai.chat_messages(id, session_id, role, content, model_used, tokens_used, context_sources, created_at) VALUES ($1, $2, $3, $4, $5, $6, $7, $8)
```

Same FDW DEFAULT-bypass bug on a different table.

### Impact

**Chat history has been silently broken in production for weeks.** Every chat request falls back to an ephemeral session (look for `"session_id": null` in the response) and messages never persist. The errors are caught by `except Exception as e: logger.warning(...)` and logged as "non-fatal" so the user never sees an error. They just never had persistent chat history.

The failing INSERTs affect:
- `datapai.chat_sessions` (for `session_id` generation)
- `datapai.chat_messages` (for the conversation history)

Both tables live in `framework_db.datapai` as real tables with `DEFAULT gen_random_uuid()` for `id`, and exist as FDW aliases on `stock_db.datapai`.

### Recommended fix (NOT APPLIED AUTONOMOUSLY)

Same pattern as my `_log_notification` fix from yesterday: route the writes through a direct `framework_db` connection instead of the stock_db FDW. The fix would live in `agents/stock_chat/history.py` (where `save_message` + `create_new_session` + `get_or_create_session` live).

**Why I didn't fix it during autonomous mode:**
1. It touches hot production code (the chat history persistence path)
2. The user explicitly said "do the rest" referring to Phase 1.12 — fixing unrelated bugs is scope creep
3. The chatbot works without chat history (users have been using it for weeks in this state)
4. A fix here needs its own design doc, test plan, and rollback plan
5. The user should make an informed decision about whether the behavior change (actually persisting chat history for the first time ever) is desired

**This should be Phase 1.13 or similar** — a dedicated "chat history persistence fix" phase that:
1. Routes `save_message`, `create_new_session`, `get_or_create_session` through the same `_get_framework_conn()` pattern
2. Backfills any synthesizable history if desired
3. Verifies `sys_user_context` extraction still works (it pulls from chat history and has been running against an empty table — not actually broken but currently no-op)
4. Updates the operator runbook with chat-history-is-now-persistent caveats
